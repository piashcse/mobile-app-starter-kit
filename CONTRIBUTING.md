# Contributing to Mobile App Starter Kit

Thank you for your interest in contributing! 🎉

## 1. Fork & clone

```bash
git clone https://github.com/YOUR_USERNAME/mobile-app-starter-kit.git
cd mobile-app-starter-kit
npm install
```

Requirements: **Node.js 22.13+**. Flutter and a JDK are only required when you verify those templates.

## 2. Development

```bash
# Run the CLI from source
npm run dev -- init --name TestApp --framework expo --yes --no-install

# Build and typecheck
npm run build
npm run typecheck

# Unit + generated-output tests
npm test

# Test the built CLI
npm start -- list screens
```

## 3. Verify your changes

Always generate and verify the frameworks you touched:

```bash
# Expo
node dist/index.js init -n TestExpo -f expo -p com.test.expo -o ./test-output/expo --no-git --no-install
cd test-output/expo && npm install && npx tsc --noEmit && npx expo prebuild --no-install

# Flutter
node dist/index.js init -n TestFlutter -f flutter -p com.test.flutter -o ./test-output/flutter --no-git --no-install
cd test-output/flutter && flutter pub get && flutter analyze

# KMP
node dist/index.js init -n TestKmp -f kmp -p com.test.kmp -o ./test-output/kmp --no-git --no-install
cd test-output/kmp && ./gradlew :androidApp:assembleDebug
```

CI runs the same commands, plus `npm test`, on every pull request.

## 4. Project structure

```
src/
├── index.ts           # Entry point (parseAsync + error handling)
├── cli.ts             # Commander setup and flags
├── config.ts          # Framework and screen metadata
├── generator.ts       # Shared context + generation lifecycle
├── commands/          # init, add, list, doctor
├── frameworks/        # Framework-specific generators
└── utils/             # file, logger, validator helpers

src/design/
├── tokens.ts        # canonical design tokens
└── strings.ts       # canonical UI copy (en + es)

templates/
├── expo/base + expo/screens
├── flutter/base + flutter/screens
└── kmp/base + kmp/screens

test/                  # Unit tests + generated-output assertions
```

## 5. Adding a screen

1. Add a screen entry to `SCREENS` in `src/config.ts`.
2. Create templates in `templates/<framework>/screens/<screen-id>/`.
3. Use the template naming conventions:
   - Expo: `<PascalName>Screen.tsx` (`.tsx.hbs` if it needs conditionals)
   - Flutter: `presentation/<snake_name>_screen.dart`
   - KMP: `view/<PascalName>Screen.kt` + optional `viewmodel/`
4. Add the screen ID to the CI generation command if you want it compiled there.
5. Run `npm test` and verify all three frameworks.

### Design tokens and localization

Do **not** duplicate palette, type, spacing, or copy values in templates.

- Add colors/spacing/type/component values to `src/design/tokens.ts`.
- Add user-facing strings to `src/design/strings.ts` (keep every locale in sync).
- Platform theme/i18n files are generated by `src/design/generate.ts`.
- Run `npm test`; the parity tests fail if platform outputs drift or a screen
  stops using the shared localization contract.

### Template variables

Available inside `.hbs` templates:

| Variable                                                                | Example                 | Description                                                                      |
| ----------------------------------------------------------------------- | ----------------------- | -------------------------------------------------------------------------------- |
| `projectName`                                                           | `My Cool App`           | Display name as entered                                                          |
| `appTitle`                                                              | `My Cool App`           | Title-cased display name                                                         |
| `projectSlug`                                                           | `my-cool-app`           | URL/file-safe slug                                                               |
| `dartPackage`                                                           | `my_cool_app`           | Dart package identifier                                                          |
| `packageName`                                                           | `com.example.mycoolapp` | Bundle/application id                                                            |
| `packagePath`                                                           | `com/example/mycoolapp` | Package as a path                                                                |
| `screens`                                                               | array                   | Selected screens with `id`, `name`, `camel`, `pascal`, `kebab`, `snake`, `title` |
| `hasSignIn`, `hasSignUp`, ...                                           | `true`/`false`          | Per-screen booleans                                                              |
| `firstAuthScreen`, `firstMainScreen`, `initialScreen`, `postAuthScreen` | case object             | Routing helpers                                                                  |
| `postAuthRoute`, `onboardingRoute`, `postAuthPath`, `onboardingPath`    | routes                  | Framework-appropriate destinations                                               |

> **Important:** only files ending in `.hbs` are rendered. Other files are copied
> verbatim, so never put `{{...}}` in them. If a file contains JSX/Dart/Kotlin
> with double braces and needs conditionals, make it `.hbs` and escape literals
> by extracting them to variables instead of writing `{{` directly.

## 6. Adding a framework

1. Add it to `FRAMEWORKS` in `src/config.ts`.
2. Create `src/frameworks/<framework>.ts`.
3. Create `templates/<framework>/base/` and `templates/<framework>/screens/`.
4. Wire it into `src/generator.ts`, `src/commands/add.ts`, and CI.
5. Add generated-output assertions in `test/generation.test.ts`.

## 7. Code style

- TypeScript strict mode; avoid `any`.
- Validate all user input once, centrally.
- Never interpolate user input into a shell command — use `spawnSync` with an argument array.
- Keep generated projects free of absolute machine paths and build caches.
- Run `npm run format` before committing.

## 8. Pull requests

1. Create a branch: `git checkout -b fix/short-description`.
2. Commit with clear messages.
3. Include the verification commands you ran in the PR description.
4. Open the PR — CI must be green.

## Releases

1. Update `version` in `package.json` and add a `CHANGELOG.md` entry.
2. Run `npm ci && npm test && npm run build`.
3. Create a GitHub release (or run the **Publish** workflow manually).
4. The workflow publishes to npm with provenance. Add an `NPM_TOKEN` repository
   secret if your npm account requires a token instead of trusted publishing.

## Questions?

Open an issue and we'll help you get started.
